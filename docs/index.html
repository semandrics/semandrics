Deterministic Core Testing
for backend services

Determininistic Core Testing is an approach for modeling and testing backend services by isolating business logic from infrastructure, making behavior deterministic, and reducing infinite input combinations to a finite set of meaningful execution flows.

Semandrics is the space to explore this approach and build tools around it.

The concept builds on three ideas:

1

Isolate the business logic from infrastructure

Separating business logic from infrastructure concerns such as HTTP, databases, messaging, or external APIs is already a well-known technique in layered architectures. Domain-Driven Design is one example of this approach. In this project, the isolated business logic is called the Core.

The idea is simple: business logic is already difficult enough on its own. Keeping it isolated makes it easier to understand, reason about, and evolve independently from infrastructure details.

2

Make the Core deterministic

A deterministic Core produces the same behavior for the same input and the same responses from external systems.

That means:

  • the same flow through the system
  • the same sequence of interactions with external systems
  • the same request data sent to those systems
  • and ultimately the same Result

Once the Core is deterministic, these behavioral flows become reproducible and analyzable.

3

Categorize input data and response data from external systems

Not all data influences behavior equally.

Some values simply pass through the system without changing the execution path. Others determine which path the system takes.

Whether a shopping cart contains two books or three usually does not matter. Whether the cart is empty does. Whether an inventory service confirms availability for two items or three changes nothing. The moment at least one item is unavailable, the flow changes.

The infinite space of concrete data can therefore be reduced to a finite set of semantically distinct categories that influence behavior. Semandrics calls these categories Variants.

Once Variants are identified explicitly, backend behavior becomes enumerable. Not every possible input — every meaningful flow.

  • Tests can be generated automatically from modeled Scenarios
  • Complete business flows can be tested at the speed of unit tests
  • Coverage gaps become easier to identify
  • Knowledge about entry points, external systems, interactions, and Variants remains inside the codebase

This project explores whether such an approach can be applied practically in real-world enterprise systems.

Ubiquitous language

The vocabulary of Semandrics

The terms in Semandrics are not arbitrary. They reflect a specific way of thinking about backend services — not as code, but as a model of behavior. Getting the vocabulary right matters, because the vocabulary shapes what you can see.

This page walks through the terms using a concrete example: a checkout service that receives a cart ID, fetches the cart, validates it, generates an order, and sends a confirmation email. Decisions happen along the way. What if the cart does not exist? What if it is empty? Each of those leads to a different path. Semandrics is interested in those paths — naming them, specifying them, and making sure none are forgotten.

1

Deterministic Core / Core

The part of the service that contains the business logic. Deterministic in a precise sense: given the same inputs and the same responses from the outside world, it always produces the same sequence of external calls and the same result. No surprises, no hidden state.

The Core does not touch infrastructure directly — no database calls, no clock reads, no UUID generation. All of that happens through explicit, annotated boundaries. Everything inside them is logic. Everything outside is infrastructure. This boundary is a design statement: here is where the business logic lives, and everything else serves it.

2

Actor

Whatever calls into the Core from the outside. In a web service, typically the HTTP layer — a controller, a request handler. The Actor is not modelled in detail. What matters is that something initiates the interaction.

3

Bounded Context PascalCase

A Bounded Context is a named domain boundary — a way of carving the business into areas of distinct responsibility. Sales, Catalogue, Finance, Store — each is a world with its own language, its own rules, its own logic.

A good indicator that you have found a boundary: the same real-world thing is represented differently on each side of it, with a different purpose and perspective. A Product in Catalogue has variants, attributes, and descriptions — the aspects relevant to how it is presented and configured. The same Product in Store has availability and a physical location — the aspects relevant to fulfillment. In Finance it carries a price and a tax class — the aspects relevant to invoicing. It is the same thing, seen through three different lenses. Each context models only what it needs to know.

In Semandrics, Entry Points and Scenarios are always defined within a Bounded Context. They belong to one, and are not shared across boundaries. Same for External Systems.

Sales Catalogue Finance Store
4

Entry Point camelCase

The annotated method through which an Actor enters the Core. Where a path begins. In the checkout example, checkout is an Entry Point — it receives a cart ID and eventually produces an order or an error.

Sales.checkout Catalogue.getProducts CustomerCare.sendTicket
5

Input Variant UPPER_SNAKE_CASE

A named category of input to an Entry Point that is meaningful for the flow. Variants are not about data — they are about semantics. A checkout Entry Point receives a cart ID and an optional coupon code. Whether a coupon is present changes the flow — WITH_COUPON and WITHOUT_COUPON are two Variants. The cart ID itself is just a UUID — whether the cart exists or not is a Response Variant on CartRepository.getCart, not a Variant on the Entry Point.

Input Variants belong to a specific Entry Point and are not shared.

Sales.checkout.WITH_COUPON Sales.checkout.WITHOUT_COUPON
6

External System PascalCase

Anything outside the Core that the Core depends on — repositories, domain services, time providers, ID generators. All of these introduce either non-determinism or infrastructure concerns, and must be controlled.

Part of the Semandrics approach is to name and model External Systems according to their semantic meaning in the Bounded Context — not according to their technical nature. So instead of a generic RandomIdGenerator or TimeService, you define an OrderIdGenerator and an OrderClock. The Access Points follow the same logic: not generateUUID but generateOrderId. This makes the intent explicit and separates semantic meaning from technical implementation.

CartRepository CustomerSupportMailService OrderIdGenerator
7

Access Point camelCase

The annotated method the Core calls on an External System. The boundary through which the Core reaches outward. In the checkout example, getCart on CartRepository is an Access Point. So is sendOrderConfirmation on OrderMailService.

CartRepository.getCart OrderMailService.sendOrderConfirmation
8

Request UPPER_SNAKE_CASE

The declared expectation of what arguments the Core should pass to an Access Point on a given path. Not chosen when composing a Scenario — produced deterministically by the Core and verified by Semandrics. If the Core is working correctly, CartRepository.getCart should be called with the cart ID that came in through the Entry Point.

CartRepository.getCart → CART_ID OrderIdGenerator.createOrderId → NO_DATA
9

Response Variant UPPER_SNAKE_CASE

A named category of response from an Access Point that is meaningful for the flow. When CartRepository.getCart is called, it might return a valid cart, an empty cart, or nothing. Each leads the Core somewhere different.

CartRepository.getCart ← VALID_CART CartRepository.getCart ← EMPTY_CART CartRepository.getCart ← CART_NOT_FOUND CartRepository ← INFRASTRUCTURE_ERROR
10

Result UPPER_SNAKE_CASE

The declared expected outcome of an Entry Point on a given path. Like a Request, it is not chosen — it is what the Core must produce if everything is correct.

Sales.checkout → ORDER_CREATED Sales.checkout → CART_EMPTY_ERROR Sales.checkout → CART_NOT_FOUND_ERROR
11

Scenario PascalCase

A complete specification of one path through the Core. One Entry Point, one Input Variant, an ordered sequence of Access Point calls each with an expected Request and Response Variant, and the expected Result. One path, fully named and declared.

The order matters absolutely. A Scenario is not a bag of assertions — it is a trace. It says: on this path, the Core calls getCart first with CART_ID, receives EMPTY_CART, and returns CART_EMPTY_ERROR. That is the whole story of that path, written down.

Sales.EmptyCartCheckout Sales.SuccessfulCheckout Sales.CartNotFoundCheckout

Methodology

How Deterministic Core Testing works

Unit tests are fast and precise, but they test small things in isolation. End-to-end tests exercise real systems, but they are slow, fragile, and expensive to maintain. Neither answers the question that actually matters most: have I covered the business behavior of this service?

Unit tests tell you the parts work. E2E tests tell you the wires are connected. Neither tells you whether the logic — the decisions, the paths, the scenarios — is fully specified and verified. Deterministic Core Testing is an attempt to work in that gap deliberately.

Identifying Bounded Contexts

Bounded Contexts are a concept from Domain-Driven Design. The short version: a Bounded Context is a named boundary within which a specific domain model applies. Inside that boundary, terms have precise meaning. Outside it, the same word might mean something entirely different — and that is fine, because it is a different context.

Identifying Bounded Contexts pays off in general — not just in Semandrics — because it reduces complexity. It forces the question of which things belong together, and why. The Product example in the Model page is a good test: if the same concept looks different depending on where you stand, you are probably looking at a boundary.

That said — not every service needs this step. If you are working on a focused service with a single clear domain responsibility, or if you are just getting started with Semandrics, it is perfectly reasonable to put everything into a single Bounded Context and give it a pragmatic name like Default or Main. The structure is still there, the IDs are still composable, and you can always split later when the boundaries become clear.

The concept comes from Eric Evans' Domain-Driven Design — the original source and still the most precise treatment of it. Beyond that, there is plenty of practical material in blogs and conference talks if you want more examples and perspectives.

Isolating the business logic

The first move is to draw a boundary. Inside: business logic. Outside: infrastructure. Everything inside is the Deterministic Core. Given the same inputs and the same responses from External Systems, the Core always does the same thing. No surprises from the clock, no variance from the database, no randomness creeping in. All of that is pushed outside and accessed only through explicit, annotated Access Points.

Drawing this boundary is a design statement as much as a testing decision. It says: this is where the business logic lives, and everything else serves it.

In Java, three annotations mark the boundary:

CheckoutService.java
// A class of Entry Points — all public methods are considered Entry Points. // This annotation is optional. Entry Point methods can also live in classes // without this annotation. @EntryPoints(boundedContext = "Sales") class SalesService { // This method is considered an Entry Point, because of the @EntryPoints // annotation of the class, and because it is a public method. public Cart createCart() { // ... } // Same here public Result<Cart> addToCart(CartId cartId, String sku, int quantity) { // ... } // Entry Points can be declared individually and names defined // that differ from the method name. @EntryPoint(name = "placeOrder", boundedContext="Sales") public OrderResult checkout(CartId cartId) { // ... } } // An External System — all public methods are considered Access Points. @ExternalSystem(boundedContext="Sales") public interface CartRepository { // Access Points can be renamed @AccessPoint(name = "getCartById") Optional<Cart> getById(CartId cartId); }

Thinking in Variants, not values

Once the Core is isolated, the next question is: what inputs lead to meaningfully different behavior?

The usual approach is to write test cases with concrete data — specific cart IDs, specific prices, specific quantities. The problem is that concrete data obscures what actually drives the behavior. Two different cart IDs produce the same path if the repository returns the same kind of response for both.

Introducing Variants is an idea to solve this issue. A Variant is not a concrete value — it is a named semantic category. The concrete data behind each Variant is implemented in Java, but the Variant itself is a named thing that can be reasoned about, counted, and composed into Scenarios. Identifying Variants forces a useful discipline: what are the genuinely different situations this service has to handle? Answering that question is, in a real sense, specifying the behavioral model of the service.

Who owns what

The boundary between Java and the UI is deliberate and worth being explicit about.

Java owns everything concrete

Entry Points, External Systems, Access Points — discovered via annotation scanning. Variants and Response Variants — implemented as named Java objects. Requests and Results — implemented as named expectations.

The UI owns only Scenarios

Named compositions of the vocabulary Java provides. The UI cannot silently break. If a Variant is removed from Java, the Scenarios that reference it fail explicitly. Java is the source of truth.

What gets verified

For each Scenario, the generated tests check three things:

1

Correct sequence

The Core calls the Access Points in the declared order. A Scenario is a trace, not a set of assertions — the sequence is part of the specification.

2

Correct arguments

Each Access Point receives the declared Request. The arguments the Core passes to External Systems are verifiable, not just the return values.

3

Correct result

The Core returns the declared Result. No infrastructure, no slow setup, no randomness. Just the logic, exercised completely along one named path.
